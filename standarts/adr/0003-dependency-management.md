# ADR 0003: Керування залежностями та контекстом запиту

- **Статус:** accepted
- **Дата:** 28.10.2026
- **Автор:** Iван Вiтковський

## Контекст

Яку проблему розв'язуємо? 2–4 речення.
без протягування 10–15 параметрів через усі шари щонайменше доступні з будь-якого рівня —
ініціалізовані ресурси, користувач-ініціатор, business-process ID, що автоматично потрапляє в кожен лог



## Чинники рішення
жодних додаткових параметрів у сигнатурах сервісів і репозиторіїв
business-process ID у кожному лозі без ручної передачі
поточна транзакція доступна репозиторію без протягування
тестованість: як підмінити залежності в unit-тестах
винесення модуля в бібліотеку з DI 
обсяг коду й крива навчання

## Розглянуті варіанти

1. AsyncLocalStorage (`node:async_hooks`) — контекст запиту
2. DI-контейнер (наприклад, awilix / tsyringe / InversifyJS)
3. Явна передача контексту параметром (`ctx`) у кожну функцію


## Рішення

Обрано **AsyncLocalStorage**, тому що збереження та наскрізного проходу контексту між асинхронними викликами у фоновому режимі без забруднення сигнатур функцій і методів додатковими параметрами

| Поле            | Звідки береться                      | Хто читає                  |
| --------------- | ------------------------------------ | -------------------------- |
| businessProcessId | генерується на HTTP-запит подію сокета  | логер |
| user            | сесія з cookie                        | сервіси |
| tx              | відкривається сервісом на бізнес-операцію | репозиторії               |

## Плюси та мінуси варіантів

### AsyncLocalStorage

- **+** чисті сигнатури
- **+** any компонент може отримати businessProcessId або поточну транзакцію у фоновому режимі
- **−** неявні залежності тобто що буде, якщо код виконується поза контекстом?

### DI-контейнер

- **+** гнучкий мокать iзi
- **−** scoped-context потрiбно створювати скоупконтейнер на кожний хттп запит

### Явна передача параметром

- **+** тестуеться iзi
- **−** боилерплейт

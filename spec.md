## Намір

VV Audio — сервіс, щоб слухати музику всім разом одночасно: одна черга на кімнату, трек грає в усіх синхронно.
Ця робота: спершу всі сценарії через HTTP API на статичних даних, потім ті самі сценарії на PostgreSQL.

## Ролі та доступи

| Роль                          | Що може                                                                                                                                                                 |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Власник кімнати               | керує відтворенням (play / pause / перемотування / наступний); ставить трек «грати наступним»; одразу видаляє будь-який трек; вирішує запити учасників; видаляє кімнату |
| Учасник                       | додає треки; одразу видаляє свої треки; чужий трек — лише запитом власнику; «наступний» — запит на пропуск                                                              |
| Преміум (властивість акаунта) | піднімає свої треки в черзі, але не вище раніше поставленого преміум-треку іншого користувача і не більше 2 преміум-треків поспіль; без ліміту кімнат                   |
| Звичайний акаунт              | додає будь-які треки; до 5 власних кімнат                                                                                                                               |
| Адмін                         | видає й знімає преміум (наприклад, за порушення правил платформи)                                                                                                       |

## Ключові запити

стейт кiмнати при входi - n+1 якщо чергу читати отдкльно, а потiм по одному треку на кожну строку ми можем це виправити через join queue_items tracks
my rooms - кiмнати, у яких юзер учасник тут теж n+1 якщо 'число трреков' в циклi по кiмнатам солюшн GROUP BY ro LEFT JOIN LATERAL
верифай ролей - яка роль юзера в кареент руме пошук по (room_id, user_id)
запрос на видалення з черги - новий або вже iснуючий визива н а кожну дiю це пошук по PK
чат рум хистори - в руми ще реалтайм чат де можно домовитись що далi слухати

## Помилки

формат ошибки { error: { code, message, bpId } }
400 - validation_error - тело запита не пройшли схему наприклад месседж де нема нiчого ghost message, логiн > 64 chars
402 - ROOM_LIMIT_EXCEEDED
401 - unauthenticated - нема сесii
403 - forbidden - не учасник кімнати або не власник
404 - нема комнати тако
409 - username_taken - логiн вже хтось використову
409 - REQUEST_ALREADY_DECIDED - запит уже вирішено інакше
409 - REQUEST_OBSOLETE - трек уже не в черзі
409 - MOVE_NOT_ALLOWED - не можна підняти трек (чужий преміум вище або більше 2 поспіль)
422 - друге тiло запроса
429 - rate_limited вiд спаму або багато запросiв
500 - INTERNAL - неочікувана помилка, деталі лише в лозі
503 - db_unavailable - бд впала або не доступна ендпоинт хелс теж верта 503

## Критерії прийняття

1. Дано: у звичайного користувача вже 5 власних кімнат. Коли: він створює шосту. Тоді: відповідь 402 ROOM_LIMIT_EXCEEDED, кімнат як і раніше 5.
2. Дано: учасник додав трек (POST /rooms/:code/queue з Idempotency-Key) і отримав 201. Коли: той самий запит з тим самим ключем надходить повторно. Тоді: відповідь 201 з тим самим треком, у черзі один трек, а не два.
3. Дано: у кімнаті 5 учасників, грає трек A, наступний — B. Коли: усі 5 клієнтів одночасно надсилають «трек закінчився» для A. Тоді: поточним стає B (черга зсунулась рівно на 1), усі отримують 200.
4. Дано: користувач є учасником 20 кімнат, у кожній по 30 треків. Коли: він відкриває «мої кімнати». Тоді: сервер виконує не більше 3 SQL-запитів. Вхід у кімнату виконує сталу кількість SQL-запитів, яка не залежить від довжини черги.

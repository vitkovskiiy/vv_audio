# ADR 0004: Стратегія тестування

- **Статус:** accepted
- **Дата:** 13.11.2026
- **Автор:** Iван Вiтковський

## Контекст і проблема

потрібно перевірити критичні правила черги хттп поведінку на реальній бд( постгрес обрав ) синхронний стан кімнати у двох користувачів і вплив змін коду на поведінку ля цього потрібні різні рівні тестів а покриття гілок має мати пороги які справді зупиняють прогін коли критерій не виконаний

## Чинники рішення

точність вимірювання покриття гілок queue.service та інших визначених модулів
швидкий цикл юнiт тестів зокрема для повторного запуску Stryker
перевірка реальних скл обмежень і конкурентних хттп запитів
ізольована чиста бд у кожному прогоні та придатність для ci в лаб 4
перевірка повного сценарію двох користувачів через клієнт і сервер
перевірка що тести ловлять неправильну поведінку а не лише виконують потрібні гілки
mutation score не нижче 80% окремо для кожного з чотирьох модулів

## Розглянуті варіанти

### 1. Раннер unit-тестів

#### Vitest — обраний

- **Плюси:** працює з наявним Vite/TypeScript стеком підтримує V8 coverage хтмл звіт і пороги гілок на окремі файли; швидкі тести зручні для Stryker
- **Мінуси:** потребує окремих дев депендесiс та конфігурації покриття це не вбудований у ноду раннер
- **Наслідки:** npm test запускає Vitest із ковереджа конфігурація фіксує queue.service на 100% гілок і пороги не нижче 80% для access idempotency та playback.service

#### Вбудований `node:test`

- **Плюси:** входить до Node.js, не потребує окремого раннера; простий для базових тестів.
- **Мінуси:** вбудований звіт про coverage в цьому проєкті показав 100% гілок `queue.service`, хоча реальне покриття його гілок було 0% нода врахувала гілки лише всередині функцій які вже викликалися такий звіт не може підтвердити критерій spec
- **Наслідки:** варіант відхилено залишення його як основного раннера створило б хибний зелений результат для вимоги 100% гілок перехід на перевірку Vitest зафіксований у `a528d70`

#### Jest

- **Плюси:** зрілий раннер з великою екосистемою та поширеними засобами мокування.
- **Мінуси:** додавав би окремий від Vite шлях конфігурації модулів і TypeScript для цього проєкту не давав переваги над уже наявним стеком
- **Наслідки:** відхилено щоб не підтримувати другий набір трансформацій і конфігурацій у проєкті використано Vitest

### 2. Залежності для інтеграційних тестів

#### Testcontainers із PostgreSQL 18 — обраний

- **Плюси:** піднімає тимчасовий PostgreSQL 18 для прогону, застосовує ті самі міграції та перевіряє справжні обмеження, транзакції й SQL; не залежить від заздалегідь зайнятого локального порту або стану постійної БД.
- **Мінуси:** потрібні Docker і час на старт контейнера; перший запуск може завантажувати образ.
- **Наслідки:** `npm run test:integration` керує життєвим циклом БД і зупиняє контейнер після прогону. Для CI у Lab 4 runner має надати доступ до Docker daemon; натомість кожен job отримує власну чисту БД без спільного стану.

#### Спільний `docker-compose` на порту 55432

- **Плюси:** простий для локальної розробки вже описаний у docker-compose.yml і відділений від стандартного порту 5432
- **Мінуси:** бд і волюм живуть довше за один прогін для чистого стану потрібно щоразу скидати схему volume паралельні прогони або ci jobs можуть конфліктувати за порт db чи state
- **Наслідки:** відхилено як джерело інтеграційного тестового середовищe Його довелося б додатково очищати й ізолювати в ci compose лишається зручним варіантом локальної db для інших сценаріїв

#### Лише сховище в пам'яті

- **Плюси:** дуже швидке просте й не вимагає docker
- **Мінуси:** не відтворює всі обмеження та поведінку postgresql а також не перевіряє реальне змагання Hhttp - запитів із db Наприклад, in-memory сховище може прийняти значення типу повідомлення, яке postgresql відхилить
- **Наслідки:** відхилено для інтеграційного рівня пам'ять лишається доречною для ізольованих unit тестів але не є доказом сумісності з productionn-db

### 3. E2E-перевірка

#### Playwright у браузері — обраний

- **Плюси:** проходить повний шлях через юайцi сервер і синхронізацію два окремі браузерні контексти мають незалежні сесії та перевіряют що другий користувач бачить кімнату чергу поточний трек і стан відтворення
- **Мінуси:** повільніший за хттп тест потребує браузерного рантайму та запуску клієнта із сервером
- **Наслідки:** npm run test:e2e запускає один Playwright-сценарій на хромiумi. ютубплеер підмінено локальним стабом щоб сценарій не залежав від зовнішньої мережі

#### Лише HTTP-сценарії

- **Плюси:** сами простий спосiб й швидкий не потребує браузера придатне для перевірки апi контрактів
- **Мінуси:** не доводить що клієнтський ui відображає стан правильно і що події синхронізації оновлюють другу користувацьку сесію
- **Наслідки:** відхилено як заміну e2e http уже перевіряється на інтеграційному рівні а браузерний сценарій додає перевірку поведінки клієнта

### 4. Мутаційне тестування

#### Stryker із Vitest runner — обраний

- **Плюси:** автоматично створює багато невеликих змін у коді та перевіряє чи тести виявляють зміну поведінки; дає mutation score для чотирьох сервісів і звіт із вижилими мутантами
- **Мінуси:** прогін значно довший за звичайний npm test бо тести запускаються повторно для мутантів це потребує більше часу й обчислювальних ресурсів у збереженому прогоні перевірено 262 мутанти у чотирьох модулях з них 145 уqueue.service точний час прогону не зберігся
- **Наслідки:** обрано для систематичного вимірювання якості тестів усі вижилі мутанти потрібно вбити тестом або класифікувати з поясненням

#### Ручні мутації для вибраних ризиків

- **Плюси:** можна змінити конкретну критичну операцію й одразу перевіритьи чи тест ловить саме цей дефект так вручну перевірено тест на гонку SQL у `c3bb3e6`
- **Мінуси:** результат залежить від того які помилки людина здогадалася внести; немає автоматичного покриття набором мутацій і підрахунку score для кожного модуля
- **Наслідки:** залишаються способом вручну перевірити окремий тест але не замінюють Stryker і mutation score з критеріїв spec

#### Без мутацій лише з покриттям гілок

- **Плюси:** найшвидший варіант і показує які гілки коду виконалися
- **Мінуси:** виконана гілка не гарантує що тест перевіряє правильний результат мутант 137 змінив locked: false на true але попередні тести лишилися зеленими попри 100% покриття гілок тестові дані створювалися через w.put() і не проходили через addTrack
- **Наслідки:** відхилено бо одного покриття недостатньо для вимоги mutation score не нижче 80% у кожному з чотирьох модулів

## Рішення

використовувати Vitest для unit-тестів і coverage testcontainers із postgresql для інтеграційних http-тестів та Playwright для e2e через браузер застосовувати Stryker до визначених сервісів а кожного вижилого мутанта вбивати тестом або класифікувати з поясненням

## Наслідки

є чотири рівні тестів unit інтеграційні http + postgresql e2e у браузері та mutation testing
unit-тести перевіряють гілки бізнес-логіки інтеграційні — http postgresql обмеження та конкуренцію e2e — узгодженість ui між двома сесіями
для інтеграційного ci потрібен docker. in-memory сховище не замінює перевірку postgresql
пороговий break у stryker оцінює загальний mutation score, а spec вимагає щонайменше 80% окремо в кожному з чотирьох модулів тому npm run test:mutation додатково запускає [`scripts/mutation-gate.ts`](../../scripts/mutation-gate.ts) скрипт читає reports/mutation/mutation.json і завершується з помилкою якщо будь-який модуль має score нижче 80%
stryker-прогін триває значно довше за npm test тому його не варто прирівнювати до швидкого unit-прогону натомість він показує чи тести виявляють зміну логіки а не лише виконують відповідну гілку

# ADR 0005: Інструменти CI/CD і стейдж

- **Статус:** accepted
- **Дата:** 24.11.2026
- **Автор:** Iван Вiтковський

## Контекст і проблема

треба ci який блокує мердж у main без зелених перевірок і cd який після мерджа сам деплоїть на стейдж доступний з інтернету
обмеження безкоштовно і без банківської карти немає ссш з github actions на машину стейджу раннер ci не має доступу до бази стейджу міграції виконуються на старті контейнера а нова версія не отримує трафік поки не готова

## Чинники рішення

1ціна 0 і реєстрація без карти
2blue-green з коробки нова версія отримує трафік лише після health check
3websocket бо застосунок працює на socket.io
4деплой без ssh і без доступу ci до бази
5один і той самий образ для staging і prod міграції на старті
6мінімум власної інфраструктури яку треба підтримувати

## Розглянуті варіанти

### 1. Де стейдж

#### Render + Neon — обраний

- **Плюси:** безкоштовний web service без карти health check path і перемикання трафіку лише на готову версію тобто blue-green з коробки websocket працює деплой через deploy hook без ssh neon безкоштовний postgresql без карти база не видаляється
- **Мінуси:** сервіс засинає після 15 хв без трафіку перший запит будить його приблизно хвилину мала потужність база render на безкоштовному тарифі видаляється через 30 днів тому база окремо на neon два акаунти замість одного
- **Наслідки:** стейдж доступний з інтернету без моєї машини health check дивиться на /readyz рядок підключення neon лежить лише в налаштуваннях render а не в github засинання і потужність записані як обмеження

#### Власний ПК + Docker + Cloudflare Tunnel + Watchtower

- **Плюси:** безкоштовно без карти потужність мого компютера watchtower сам тягне новий образ з ghcr ssh не потрібен
- **Мінуси:** стейдж доступний лише поки увімкнений мій пк blue-green треба збирати руками два контейнери і проксі більше місць де щось може зламатися
- **Наслідки:** відхилено бо стейдж має бути доступний завжди а ручний blue-green це багато роботи і ризику заради того що render дає з коробки

#### Koyeb / Fly.io / Railway

- **Плюси:** paas з health check і деплоєм готового образу у fly.io є стратегія bluegreen
- **Мінуси:** koyeb з лютого 2026 вимагає карту fly.io теж вимагає карту railway дає лише пробний кредит
- **Наслідки:** відхилено бо карти немає а пробний кредит закінчиться і стейдж зникне

### 2. Як образ потрапляє на стейдж без SSH

#### GHCR + deploy hook Render — обраний

- **Плюси:** образ збирається один раз у ci з git_sha = sha коміту той самий образ піде і на prod деплой це один http-запит на hook без ssh ci після деплою може перевірити /version і побачити що стейдж справді на новому коміті
- **Мінуси:** урл хук тжо секрет я його закинув в гит секреты пакет у гшср має бути публічним щоб рендер його забрав перший деплой падає поки сервіс на рендеро ще не створений
- **Наслідки:** деплой іде лише після зеленого ci на main секрет RENDER_DEPLOY_HOOK_URL у налаштуваннях репозиторію ci не знає нічого про базу

#### Автодеплой Render із Git (Render сам збирає Dockerfile)

- **Плюси:** нічого не треба налаштовувати в actions render сам бачить push у main і збирає образ
- **Мінуси:** у режимі after ci checks pass render чекає зелений ci але образ збирає сам render з того самого коміту тобто задеплоєно не той образ який перевірив ci а зібраний заново гит_шаa треба передавати окремо ci не бачить чим закінчився деплой
- **Наслідки:** відхилено бо на стейдж має йти саме той образ який пройшов перевірки а не перезібраний плюс у моєму варіанті крок cd після hook чекає поки /version на стейджі покаже sha нового коміту тому зелений cd означає що стейдж справді на новій версії а при автодеплої render ci про це не знає

### 3. Conventional commits

#### commitlint на заголовку PR + лише squash + локальний хук — обраний

- **Плюси:** при squash повідомлення коміту в main береться із заголовка pr тому однієї перевірки заголовка досить щоб у main усі коміти були за conventional commits перевірка перезапускається при правці заголовка локальний хук commit-msg ловить помилки ще до коміту правила одні й ті самі
- **Мінуси:** працює лише разом зі скуаш історія гілки в main не зберігається проміжні комвіти в гілці можуть бути будякими якщо обійти хук но верифай
- **Наслідки:** у рулсет дозволений лише squash merge commit вимкнений

#### Перевірка кожного коміту в PR

- **Плюси:** кожен коміт гілки за правилами пррацює і з merge commit
- **Мінуси:** одна помилка в старому коміті змушує переписувати історію гілки рбільше роботи для одного розробника а при squash ці коміти все одно не потрапляють у main
- **Наслідки:** відхилено бо при squash перевіряти кожен коміт зайве в main потраопляє лише заголовок pr

## Рішення

стейдж render + neon образ збирає ci публікує в ghcr і викликає deploy hook render без ssh conventional commits перевіряються commitlint на заголовку pr разом зі squash-мерджем і локальним хуком commit-msg

## Наслідки

- **краще:** брудний pr не змерджити прямий push у main неможливий кожен мердж сам деплоїться на стейдж без простою /вершиона показує який коміт запущено ci не має доступу до бази
- **гірше / обмеження:** стейдж засинає після 15 хв перший запит до хвилини мала потужність два зовнішні акаунти історія гілок не зберігається через squash
- **пам'ятати далі:** lab 5 навантаження на безкоштовному тарифі покаже саме обмеження тарифу а не застосунку холодний старт треба враховувати в замірах міграції структури лише expand/contract щоб стара версія працювала на новій схемі
